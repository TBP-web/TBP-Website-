# The Bandhan Project (`tbp;`) — Website & CMS

Official one‑page website for **The Bandhan Project**, plus a built‑in admin panel
that lets non‑technical editors change almost everything on the page — navigation,
hero, sections, footer, links — without touching code.

- **Live site:** `index.html`
- **Admin panel:** `admin.html` (default passcode `admin123` — change it)
- **No build step. No server. No database.** Just static files.

---

## 1. How the site is built (the mental model)

Everything you see on the page is **data** rendered by a small amount of
JavaScript. There is one content object with a section for each part of the site.
Three layers decide what a visitor actually sees:

| Layer | File | Who it affects | How it changes |
|------|------|----------------|----------------|
| 1. Built‑in defaults | `assets/js/site-data.js` (`DEFAULT_SITE_DATA`) | Everyone (fallback only) | Edited by a developer |
| 2. **Published content** | `assets/js/content.js` | **Every visitor** | Exported from the admin panel, then committed/deployed |
| 3. Local draft | the editor's browser `localStorage` | **Only that browser** | Saved automatically as you edit in the admin panel |

**Plain English:**

- A normal visitor sees **`content.js`** (or the built‑in defaults if that file is
  missing). Their browser never stores anything.
- When you open the admin panel and click *Save*, your edits are kept **only in
  the browser you're using**. Nobody else sees them yet — this is your *draft*.
- To make the draft live for the world, you **Publish**: download a fresh
  `content.js` from the admin panel and deploy it (details in
  [§6](#6-publishing-content-changes-after-deployment)).

This design means the site can never "go down" because of a content edit, a
database outage, or a bad save — it's just HTML/CSS/JS on a CDN.

## 2. Pages

The site is now **multi‑page**, but there are still only three HTML files —
everything else is generated from your content:

| File | What it shows |

| `index.html` | The homepage (all the sections below) |
| `event.html?id=<id>` | One event's full page — cover image, full story, photo gallery. Every jigsaw card on the homepage links here. |
| `page.html?slug=<slug>` | A custom page you built in the admin panel (Volunteer, Programs, FAQ …) |

The header and footer are identical on every page and are managed in one place.

## 4. The Admin Panel

### Opening it

Any one of these:

1. Go to **`/admin.html`** (or `/admin` on Netlify/Vercel) directly.
2. From the live site, click the small **🔒** at the very end of the footer
   copyright line.
3. Press **Ctrl + Shift + A** (Windows) / **Cmd + Shift + A** (Mac) anywhere on
   the live site.

Enter the passcode (default **`admin123`**). You stay logged in until you close
the browser tab or click **Log Out**.

### The tabs

**Content Management**

| Tab | What you can change |
|-----|---------------------|
| **Jigsaw Past Events** | Add / edit / delete events. Each event: title, category, date, time, location, up to 4 photos (drag‑and‑drop upload, auto‑compressed), a **Short summary** (shown on the jigsaw card), a **Full story** (Markdown, shown on the event's own page — leave blank to reuse the summary), and an *Active* toggle. Every event automatically gets its own page at `event.html?id=…`. |
| **Hero & Branding** | Brand full name & short name, hero headline (supports a `<span>` for the coloured highlight), hero sub‑text, both hero buttons (text + link), hero background image. |
| **About & Stats** | About heading & highlight, narrative, **Vision** heading + statement, **Mission** heading + statement, CTA button, side image, and the **4 impact counters** (number + label each). |
| **yKnot Project** | Show/hide toggle, image, badge, title, tagline, description (blank line = new paragraph), button text + link. |
| **Founder's Note** | Portrait photo, badge, quote, the full letter (blank line between paragraphs), name, designation. |
| **Moments & Gallery** | Add photos (title + subtitle + image), remove photos. |
| **Contact & Footer** | *Contact:* section heading, intro line, email, phone, address.<br>*Footer:* brand name & tagline, bio, copyright, **social icons** (add/remove, pick network, paste URL), **footer link columns** (add/remove whole columns, add/remove links inside, point each at `#section` or an external URL), and the **newsletter box** (show/hide + heading + text). |

**Site Structure**

| Tab | What you can change |
|-----|---------------------|
| **Navigation & Layout** | *Top Navigation Menu:* add, rename, reorder (↑ ↓), or remove menu items — each is a label + a link (`#about`, `page.html?slug=…`, or any `https://…` URL).<br>*Homepage Sections:* switch whole sections on/off.<br>*Floating WhatsApp Button:* show/hide, label, colour, and the group invite link. |
| **Custom Pages** | Build extra pages (Volunteer, Programs, FAQ …). Each page has a title, URL slug, optional hero image, Markdown body, and an "add to top menu" toggle. Lives at `page.html?slug=<slug>`. A sample **Volunteer** page ships with the site — edit or delete it. |

**Markdown** (used in event Full stories and custom‑page bodies): blank line = new
paragraph · `## Heading` / `### Subheading` · `- ` for bullet points ·
`**bold**` · `*italic*` · `[link text](https://…)` · `![alt](image-url)`.

**Administration**

| Tab | What you can change |
|-----|---------------------|
| **Security & Publishing** | **Publish** (download `content.js`), **Discard local changes**, change the admin passcode, export a **JSON backup**, restore from a backup. A banner at the top tells you whether you have unpublished changes. |

### How saving works

- Every *Save* button writes to **this browser only** (your draft).
- The live site (open `index.html` in another tab) updates **instantly** while
  you edit — even across multiple open tabs — so you can preview as you go.
- Images you upload are shrunk to max 1000px and embedded directly into the
  content as data URLs (no separate upload server needed). Keep uploads
  reasonable — very large images bloat `content.js`.

## 6. Publishing content changes after deployment

Edits in the admin panel are **local until you publish**. To push them live:

1. Make and **Save** all your edits in the admin tabs.
2. Go to **Security & Publishing**. The banner should say *"You have unpublished
   changes."*
3. Click **Download content.js for publishing**. Your browser saves a file
   named `content.js`.
4. Put that file at **`assets/js/content.js`** in the project, replacing the old
   one.
5. Deploy the change:
   - **Git‑connected host (recommended):** commit and push.
     ```bash
     git add assets/js/content.js
     git commit -m "Update site content"
     git push
     ```
     Netlify / Vercel / Cloudflare Pages redeploy automatically in ~30–60s.
   - **Drag‑and‑drop host:** re‑upload the whole folder (or just the file).
6. Hard‑refresh the live site (Ctrl/Cmd + Shift + R) to confirm. Other visitors
   get it within a minute (HTML and `content.js` are set to revalidate on every
   request — see `_headers` / `netlify.toml`).

> **Tip:** After publishing, click **Discard local changes** in the admin panel
> so your browser stops showing your (now‑published) draft and starts tracking
> the live file again.

**Keep a backup habit:** use **Export JSON backup** occasionally and keep the
file somewhere safe. If `content.js` is ever lost or broken, *Restore from JSON
file* rebuilds everything.

## 7. Deployment

The site is plain static files, so it works on any static host. Pick one:

### Option A — Netlify (easiest, recommended)

**Drag‑and‑drop (no Git):**
1. Go to <https://app.netlify.com/drop>.
2. Drag the **project folder** onto the page.
3. Done. You get a `something.netlify.app` URL. `netlify.toml` and `_headers`
   are picked up automatically.

**Git (auto‑deploy on every push):**
1. Push this repo to GitHub/GitLab.
2. Netlify → *Add new site* → *Import from Git* → pick the repo.
3. Build command: **leave empty**. Publish directory: **`.`** (the repo root).
4. Deploy. Every `git push` now redeploys.

### Option B — GitHub Pages (free, Git‑based)

1. Push the repo to GitHub.
2. Repo → **Settings → Pages** → Source: *Deploy from a branch* → branch `main`,
   folder `/ (root)` → **Save**.
3. Site goes live at `https://<user>.github.io/<repo>/` in a minute or two.
   > GitHub Pages ignores `_headers` / `netlify.toml`, and `/admin` won't
   > redirect — use the full `/admin.html` URL. Everything else works.

### Option C — Cloudflare Pages

1. Cloudflare dash → **Workers & Pages → Create → Pages → Connect to Git**.
2. Framework preset: **None**. Build command: **empty**. Output directory: **`/`**.
3. Deploy. `_headers` is honoured.

### Option D — Vercel

1. Vercel → *Add New → Project* → import the repo.
2. Framework preset: **Other**. Build & output settings: leave defaults (no
   build). `vercel.json` handles headers and the `/admin` clean URL.

### Custom domain & HTTPS

All four hosts give **free automatic HTTPS**. To use `thebandhanproject.com`:

1. In the host's dashboard: *Domains → Add a domain* → enter your domain.
2. At your domain registrar, add the DNS records the host shows you (usually a
   `CNAME` for `www` and either an `A`/`ALIAS` record or nameserver change for
   the apex).
3. Wait for DNS to propagate (minutes to a few hours). The host issues the SSL
   certificate automatically.
4. Update `robots.txt` — uncomment and set the real `Sitemap:` line if you add a
   sitemap later.

## 8. Keeping the site healthy (so it never stalls)

The site has **no backend**, so there is no server to crash, no database to fill
up, and no dependency that can expire. What you still need to do:

| Concern | What to do |
|--------|------------|
| **Hosting uptime** | Netlify / Cloudflare / GitHub / Vercel all run on global CDNs with ~99.9%+ uptime on the free tier. Nothing to maintain. |
| **Domain** | Renew it before it expires (set auto‑renew at your registrar). An expired domain is the single most common way a static site "goes down." |
| **HTTPS certificate** | Auto‑renewed by the host. Nothing to do — just don't remove the domain from the host. |
| **Content backups** | Every few edits, **Export JSON backup** from the admin panel and store it (Google Drive, email to yourself, etc.). Also: `content.js` lives in Git, so every publish is already versioned. |
| **`content.js` integrity** | If it's ever malformed, the site automatically falls back to the built‑in defaults in `site-data.js` — it won't show a blank page. Fix it by restoring from a JSON backup and re‑publishing. |
| **Images** | Every uploaded photo is stored *inside* `content.js`, which every visitor downloads. A handful is fine; a large event archive is not. **Once you have more than ~15–20 photos across the whole site, switch to file paths:** drop the image files into `assets/images/` (commit them), then paste `assets/images/your-photo.jpg` into the image field instead of uploading. Or use a free image host (Cloudinary, etc.) and paste its URL. Aim to keep `content.js` under ~500 KB. |
| **Browser support** | Targets all current browsers (Chrome, Edge, Firefox, Safari, and their mobile versions). No IE. |
| **Admin passcode** | It is **light protection only** (see below). Rotate it if it leaks. |
| **Dependencies** | The bundled jQuery/Bootstrap are old but frozen and self‑hosted — they will keep working indefinitely. There is nothing to `npm update`. |
| **After any deploy** | Open the live URL, hard‑refresh, click through the nav, open `/admin.html`, and confirm the footer links work. Takes 60 seconds. |

### If the site ever looks broken

1. Hard‑refresh (Ctrl/Cmd + Shift + R).
2. Open the browser console (F12) and look for a red error.
3. Most likely cause: a bad `content.js`. Replace it with a known‑good copy from
   Git history or a JSON backup, then redeploy.
4. Worst case: delete `assets/js/content.js` entirely and redeploy — the site
   reverts to the built‑in default content and keeps running.

## 9. Security

The admin passcode is stored in the content and checked in the browser. **Anyone
who views the page source can read it.** It only stops casual visitors from
fiddling with the admin forms. Publishing still requires access to your
host/repository, so a leaked passcode cannot change the live site by itself — but
you should still treat it as non‑secret.

For real access control on `/admin.html`, use your host's built‑in protection:

- **Netlify:** *Site settings → Access control → Password protection* (or
  Netlify Identity for per‑user logins). You can also restrict it to a path.
- **Cloudflare Pages / Zero Trust:** add an **Access policy** for
  `yoursite.com/admin.html` (email‑code or SSO login).
- **Vercel:** *Project → Settings → Deployment Protection* (Standard Protection
  or password).

Also keep `robots.txt` (already included) so search engines don't index the
admin page.

## 10. Local development

No tooling required. Either:

- **Just open `index.html`** in a browser (works, but `content.js` may not load
  from `file://` in some browsers — use a server for a faithful preview), or
- **Run a tiny static server:**
  ```bash
  npx serve .
  # then open http://localhost:3000
  ```

To change the **built‑in default content** (the fallback that ships in
`site-data.js`), edit `DEFAULT_SITE_DATA` at the top of
`assets/js/site-data.js`. To regenerate `content.js` from those defaults:

```bash
node -e "global.window={addEventListener(){},dispatchEvent(){}};global.localStorage={getItem:()=>null,setItem(){},removeItem(){}};global.sessionStorage=global.localStorage;require('./assets/js/site-data.js');require('fs').writeFileSync('assets/js/content.js','window.TBP_PUBLISHED_CONTENT = '+JSON.stringify(window.TBP_DEFAULT_CONTENT,null,2)+';\n')"
```

(Normally you never do this — you use the admin panel's **Publish** button.)

## 11. Tech notes

- **Rendering:** `render-site.js` runs on every page. It reads the merged content
  object, injects the shared header/footer into `event.html` / `page.html` (index
  keeps its own), then renders the nav, homepage sections, event pages, custom
  pages and the WhatsApp button. Re‑renders on every `tbp_data_updated` /
  cross‑tab `storage` event.
- **Events board:** a CSS‑grid "jigsaw" — zero‑gap pieces with connector knobs
  (`::before` / `::after`) and socket notches, responsive to a single column on
  phones. Each piece is a link to `event.html?id=…`.
- **Custom pages & event stories** use a tiny built‑in Markdown subset (headings,
  paragraphs, bullets, bold/italic, links, images). Input is HTML‑escaped first.
- **Animations:** one lightweight `IntersectionObserver` reveal system (no
  `animate.css` / WOW.js).
- **Icons:** LineIcons 2.0 (`lni lni-*`).
- **Search engines & sub‑pages:** `index.html` is plain HTML and indexes fine.
  Event pages and custom pages are rendered by JavaScript, so their text is
  weaker for Google. Fine for a nonprofit whose visitors arrive via social media,
  the WhatsApp group, and direct links. Making those pages fully SEO‑friendly
  would need a build step — a deliberate trade against the current
  "no server, no build" simplicity.
